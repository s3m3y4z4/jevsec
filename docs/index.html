JEVSEC is a local decision layer for authorized security testing and CTF work. Scanner findings and engagement observations go in; an explained, ordered queue comes out. It sends no traffic to your targets, and it never decides for you — below the confidence threshold, or on any error, a human reviews.

How a finding is judged

No prompt engineering against a chat window. Every decision is an atomic question about redacted text, answered with a probability, and recombinated into scores by code you can read.

  1. Redact at the boundary. Hex blobs and base64-like strings are replaced with placeholders, bodies truncated at a configured length.

    response_snippet: “archive digest [hex:redacted] listed in index”

  2. Ask atomic questions only. The model answers typed questions — a verdict, a boolean fact, a choice — never “assess this finding”. It never sees the engagement objective or scenario words: it judges facts.

    noul → 0.79 · choice → true_positive 0.86 · score → 0.31

  3. Recombine in code. Rubrics live in TOML, not in the model: rules over question thresholds produce a 0–4 impact, with a declared default rule. Incomplete rubrics are rejected at startup.

    rules = { q_egress ≥ 0.5, q_reachable ≥ 0.5 } → score 3

  4. Gate on doubt. Below the confidence threshold, or on any error, the record goes to human review. Nothing is silently discarded or auto-approved on error.

The engine we trained — and what we measured

This repository ships no model weights; any System One-compatible backend works — point base_url at it and JEVSEC speaks the same wire contract: typed questions in, probabilities out.

Our backend is jevsec-003 (third iteration) — a LoRA fine-tune of XHToken/Spark-X2.5-4B (Apache-2.0), trained on a private, de-identified dataset of 317 security observations with human-verified labels: where the operator’s verdict disagreed with the model, the operator’s verdict won. One Q8_0 GGUF, one forward pass per question set, zero generated tokens; it runs on a single consumer GPU (8 GB VRAM is enough for Q8_0).

What it is not — the same limits are declared on the model card:

  • Probabilities are not calibrated on your domain: temperature scaling on your own labeled data is required before any threshold-based decision.
  • Prompt injection moves the model: injected instructions in finding bodies can push probabilities, which is measured, replicable, and exactly why the auto gate ships disabled.
  • Small training set: an experiment that learns operator judgment, not a production classifier. Validate on your own material first.

Three surfaces, one daemon

The whole cycle runs without any AI agent — from the CLI and from the browser console, with identical effects. If you drive an agent, six optional MCP tools expose the same API.

live-triage

Scanner findings in — one JSON object per line — an ordered TriageRecord queue out, with auto/review gates.

every judgment carries its probability and the question that produced it

prioritize

Engagement observations per declared objective — ship domain_admin, user_flag, rce_app, or declare your own in TOML with no code changes.

the model answers atomic questions; the code recombinates them into 0–4 impact

live-console

The jevsecd daemon keeps real-time sessions: local API, browser console, optional MCP tools for agents.

sessions persist on disk; a restart loses nothing

Boundaries, not features

These are constitutional — written into the project’s constitution, not toggles that ship on.

no autonomous execution

The tool decides and sorts. It launches no commands and sends no traffic to your targets.

Optional assisted execution exists, off by default: template-only commands, per-action human confirmation, allowlist and target scope, one audit line per action before the daemon answers.

local by default

The only network connection is to the decision backend’s base_url.

A non-loopback backend is opt-in and requires HTTPS plus a token, or the tool refuses to start. Only redacted judgment text ever travels; the daemon and the console stay on loopback in every configuration.

always gated

Below threshold, or on any error, a human reviews.

Nothing is ever silently discarded or auto-approved on error.

auto gate stays off

Shipped disabled, on measurement: injections in response bodies can push the model over threshold.

The adversarial measurement ships in the repository and is replicable with harness/run_adversarial.py. Auto re-arms only after a certified mitigation or recalibration on real data.

Five minutes, no GPU

Linux, Python 3.11+ (tested on 3.13), git. The deterministic development backend is enough to see the whole cycle; a real engine is a base URL away.

bashfrom clone to first triaged queue
# deterministic dev backend (no GPU, no weights)
python3 harness/mock_systemone.py &

# triage the synthetic sample
PYTHONPATH=src python3 -m jevsec triage \
  --input data/samples/live_triage_findings.jsonl \
  --config config/live-triage.toml \
  --base-url http://127.0.0.1:8099

# expected: one triaged record per line on stdout,
#           the ordered queue on stderr, exit 0

Then open a session, feed observations, and read the queue — the full cycle also runs from the browser console at 127.0.0.1:7860. For a real engine see the engine section.
